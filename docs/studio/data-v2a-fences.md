# Data batch2A: isolated session-level recording and deletion fences

This adds `FencedPracticeRepository` beside batch1, without changing its adapter, `PracticeEngine`, v22 storage, the controller, UI, or published Site. It only accepts explicit `lingotrace-dev-fenced-*` database names and refuses construction and every storage opening in production. Schema version 1 belongs to this new namespace; nothing is migrated. Tests use original fixtures in isolated databases. Passing emulated IndexedDB tests is not evidence of a real-browser reload or product/device acceptance.

## Explicit adoption boundary

Construct with `{databaseName, indexedDB?, initialRecordingEnabled?}`, then await `prepare()`. The current page starts OFF. Only a newly created development database may take the explicit initial preference; the durable preference wins on later instances and reloads. `initialRecordingEnabled` defaults to false.

`beginRecordedSession(initialSnapshot)` accepts only a validated, sessionStarted-only snapshot with a never-used session ID. It atomically creates the initial fact and head, then returns an opaque frozen `WritePermit`. `save(snapshot, permit)` requires that exact permit from that repository instance. A permit pins the session ID, page epoch, local session epoch, durable global generation, and session generation; it is never refreshed or restored from disk. Instances can load previous sessions but cannot resume their recording with a new permit. A failed admission consumes its ID on that page; retry with an explicitly new recording segment.

`setRecordingEnabled(true)` enables future admission only after its durable setting commits, and returns `requiresNewRecordedSession: true`. Neither toggle resets, ends, submits, awards, or otherwise calls the current `PracticeEngine`. Temporary practice can continue in RAM and be explicitly exported. A later controller/user must explicitly choose the boundary for a new recording segment. Passing any practiced snapshot, a previously observed off-period ID, or an existing/deleted durable session ID to admission fails. An otherwise unseen, pristine sessionStarted-only shell has no answer or practice history and is admitted as an explicit new segment; this API does not infer its construction time from wall clocks.

## Transaction and revocation contract

- `events` is the only fact store. `heads` contains revision/generation metadata; reads derive projections using canonical replay. `control` contains only the recording preference and global/deletion/clear counters. `tombstones` contains only session ID, session generation, and deletion watermark, with no answers, drafts, attempts, material text, audio, or timestamps.
- Every admission/save reads the control, head, tombstone, and current facts inside the same readwrite transaction that writes facts/head. Save requires the existing head and matching generations; it cannot recreate missing/deleted parents. Matching canonical event prefixes are idempotent, stale prefixes preserve newer facts, and divergent payloads fail atomically.
- Turning recording OFF synchronously disables this page, increments its epoch, and aborts tracked admission/save transactions before awaiting IndexedDB. Queued operations and callbacks retain their original permits and recheck them before opening, before writing, and before returning. OFF does not delete existing data; `load(sessionId)` remains available.
- Every committed recording-setting operation advances the global generation. Therefore another instance's old permits still fail after an OFF/ON cycle. Transactions serialize through the shared control store. Each local operation reserves its queue position before notifying subscribers, so a subscriber's reentrant newer setting intent also commits later and wins durably. There is no queued autosave retry and ON never backfills off-period practice. A foreign write that committed before the OFF transaction is ordered before OFF; after OFF commits, durable checks reject stale writes. Cross-tab live UI synchronization is not implemented.
- `deleteSession(id)` synchronously fences that ID on this page and aborts its active writes. One durable transaction advances the deletion watermark/session generation, deletes all its facts/head, and retains a minimal tombstone. Reusing that ID, replaying an older prefix, or appending a newer suffix with any old permit fails.
- `clearPracticeData()` synchronously revokes all local permits and aborts active writes. One durable transaction advances the global generation and clear/deletion watermarks, removes all facts/heads, and retains tombstones for all known IDs, including any orphan fact keys. Previously retained deletion lineage stays. The recording preference itself is unchanged. The same database cannot resurrect deleted IDs using old handles; backup import is not implemented.

Successful delete/clear receipts are returned only after transaction completion. A failed delete/clear cannot claim durable deletion; the current page's affected old permits stay revoked. A failed OFF preference write leaves this page OFF and reports `settingsState: 'not-persisted'` and an explicit `settingsError` stating there is no other-tab or reload guarantee. Successful reads change only read metadata, never clear a newer write error. Operation sequencing prevents older setting/write callbacks from overwriting a newer operation's status. `close()` synchronously fences this instance, drains/aborts writes and closes its connection; create a new instance to reopen.

## API results and status

- `prepare()` and `setRecordingEnabled(boolean)` return the current status.
- `beginRecordedSession(snapshot)` returns `WritePermit`; `save(snapshot, permit)` returns `{sessionId, storedSequence, disposition}`, with disposition `appended`, `already-present`, or `newer-preserved`.
- `deleteSession(id)` returns `{sessionId, deleted: true, sessionGeneration, deletionWatermark}`. `clearPracticeData()` returns `{cleared: true, globalGeneration, clearWatermark}`.
- `load(id)` returns a canonical `PracticeSnapshot` or null. `getStatus()` and `subscribe(listener)` expose immutable status updates. Status fields are `state`, `pending`, `error`, `readError`, `lastLoadedSequence`, `prepared`, `recordingEnabled`, `durableRecordingEnabled`, `settingsState`, `settingsError`, and `requiresNewRecordedSession`. `durableRecordingEnabled` is the last observed durable preference, not a cross-tab notification guarantee. Settings state is `unprepared`, `pending`, `persisted`, or `not-persisted`.

## Explicitly deferred

This batch implements session-level fences only. It does **not** delete a single attempt such as a1 while preserving a2. Batch2B must define canonical redaction and replay semantics for per-attempt deletion; filtering a projection is insufficient. No attempt-level deletion, dependent assessment/regrade cleanup, review scheduling, award identity, backup/import merge, migration, media cancellation, AI/cloud credentials, or production integration is claimed here. Direct database-file replacement, user exports, browser sync/backups, and other independently stored copies are outside this isolated adapter's deletion guarantee.
